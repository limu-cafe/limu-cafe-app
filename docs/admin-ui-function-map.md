### 立替操作の見直し（2026-11-20、未配備）

一人が複数回買い出しした分を、一度に返す場面を基本にする。未精算一覧の主対象は立替者で、購入明細はその内訳にする。以前のde3f321の明細別精算UIは、本人から「立替精算を別々でするわけ無いんだよ」と指摘され、以下に置き換えた。

- 未精算を立替者のUUIDでまとめ、氏名・件数・合計額を表示。同姓同名や記録者の違いを返金先の根拠にしない。立替者未登録は別枠で確認し、一括対象へ混ぜない。
- 人を選ぶと、その人の未精算を最初から全件選択した内訳を表示。通常はそのまま全件の合計を確認し、現金をまとめて渡したことを一度記録する。必要な場合だけ一部の明細を外せる。
- APIは一括リクエストを一度送信し、DBトランザクション内で全明細・金庫の出金・精算控え・監査を確定する。別人・金額変更・既精算・不明な対象があれば全体を拒否する。選択内容と操作IDが同じ再試行は同じ控えを返し、二重出金しない。旧明細別APIも同じDB関数に接続し、競合時の二重出金を防ぐ。
- 実際の返金は一回。既存の金庫照合を維持するため、内部の出納は各購入記録に紐づく行を同じトランザクションで保存する。全件をまとめた控えを残し、完了画面と監査ログから内訳を再表示できる。
- 立替の登録は下記の「買い物を記録」に統合。商品と備品・雑費を同じ明細表に入力し、商品だけ在庫へ反映する。在庫を既に追加した場合は「購入のみ」に切り替える。閉じる・失敗でも入力を保持し、成功時だけ初期化する。
- 未精算は全期間・全件を取得し、過去の履歴は40件ずつ表示する。取得失敗を未精算0件と表示しない。古い明細へのリンクは、その立替者のまとめ精算へつなぐ。履歴の個別明細と既存登録機能は保持する。

DB移行 `20261120062027_batch_advance_reimbursements.sql` は控えの新規テーブルとservice_role専用関数だけを追加する。履歴の金額・残高・在庫は書き換えない。**移行を適用してからアプリを配備すること。** 未適用時は503で停止し、不安全な個別REST更新へフォールバックしない。今回、本番・テストのDBや配備は変更していない。

型検査・全184テスト（skip 0）・本番ビルドで検証。隔離したPGliteで、別人混入/金額競合/既存出金/監査失敗の全件ロールバック、同一操作の再試行、旧APIとの実行順、権限と残高/在庫の不変を確認する。PGliteは単一接続のため多接続負荷/デッドロックの実測ではない。本番での実精算、本人の使用感の評価は未実施。

## 管理者による注文の残高精算

利用者一覧 → 選択した利用者の注文（古い未精算は「取引・未精算」）→ 注文詳細 → 「利用者の残高から精算」。主メニューに精算専用の新しい入口は増やさない。既存の「精算完了」は現金受領と誤解しないよう「現金を受領」と表記する。

対象は処理完了済み・未精算の現金注文と現金回収予定の後払い注文。ポイント利用後の未精算額、現在残高、精算後残高を表示し、本人確認・現金未受領の確認と精算理由を要求する。残高不足や更新競合では実行せず、注文詳細を保持する。元の支払い方法、残高の前後、理由は注文詳細と監査記録から確認できる。

管理者認証は既存のSlackログインとユーザーに結び付いた署名付き管理パスワード確認を使う。ブラウザが指定した利用者ID・操作者IDは採用しない。新しいDB関数はservice_roleだけ実行できる。注文・残高・要回収額・変更前の証跡・監査を1トランザクションで保存し、重複要求は引き落とさない。現金受領・一括精算・チャージ返金も同じロック順で処理する。古い残高スナップショットを上書きする経路は相対増減へ置換する。

購入当時の明細・在庫・ポイントは変更しない。現金を受領したことにはせず、未払いのチャージ代は要回収に残す。実際の支払い方法を残高へ変更するため、既存の注文返金・取消は引き落とした残高を1回だけ戻せる。精算記録自体は削除しない。

DB移行は履歴行の金額・残高を修正せず、準備完了フラグと変更証跡の表、service_role専用関数を追加する。新規注文・チャージは処理完了まで精算を拒否する。移行から新コードの配備までに旧コードが作った行があれば未準備のまま拒否されるため、配備前後に件数を確認し、推測で準備完了や実精算を実行しない。既存SQLをまとめて再適用しない。

隔離PostgresとモックUI/APIで回帰検証する。実利用者への精算や残高補正を検証として実行しない。既存の利用者向け残高払い試作はこの管理者機能には含めない。


### 複数注文の残高精算

取引の「要回収」で未精算注文を利用者ごとにまとめる。各注文のチェック、同一利用者の全選択、選択した注文の精算確認を、その利用者の注文一覧内に置く。別の利用者・チャージ代・サブスク支払は選択に混ぜない。確認画面で対象の明細と日時、ポイント控除後の合計、精算前後残高、理由、本人/現金未受領確認を表示し、戻ると選択を保持する。

一括APIは対象者と各注文の金額を検証し、既存の個別精算関数を1トランザクション内で実行する。1件でも状態変更・金額変更・残高不足があれば、注文・残高・個別証跡・一括証跡・監査を全件ロールバックする。利用者ごとの既存ロックを共用し、操作IDと正規化した注文集合で同じ要求の再送を冪等化する。別の要求へ同じ操作IDを使った場合や、一部だけ精算済みの新しい要求は拒否する。新しい一括証跡はservice_roleだけ読取/追加可能で、クライアント権限と更新削除権限は与えない。既存の履歴や残高は移行時に変更しない。
