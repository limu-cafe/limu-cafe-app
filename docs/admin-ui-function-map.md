## 対象と近道

- 商品から在庫へは要補充時、利用者から未精算へは要回収時に近道を出す。
- 金庫の差額から該当する確認記録へ、未精算の立替からその明細へ進む。
- 個人の契約から該当するサブスク商品と契約IDへ、監査ログから該当記録へ進む。
- 選択IDと情報ビューはURLで保持する。移動だけで精算・更新は実行しない。

## 試作と検証

試作用アプリは`/private/tmp/limu-ui-preview`、`http://127.0.0.1:3100/admin`。実際の管理コンポーネントに`prototypes/admin-preview/fixtures.ts`と`full-fixtures.ts`の架空データを渡す。利用者・商品・契約などのIDを共通にし、関連先で別の対象を表示しない。

`readonly-middleware.ts`は隔離した試作用アプリ専用。`/api/*`のGET/HEAD以外を405で拒否する。本体のmiddlewareには入れない。本番DB・認証には接続せず、保存・精算・送信の成功を確認する環境ではない。

型検査および7ファイル61件の回帰テスト成功。追加した10件では契約/定額商品、立替の商品/雑費、金庫の手動入出金/雑費/0円実測/枚数優先、在庫追加の二重送信と再試行、要望の一括対象、キャンペーン、移行、古い立替の指定読取を確認。DB・APIはモックで、実データ更新試験ではない。

ブラウザで管理メニュー12画面を1440px/689pxで表示し、main/bodyの横はみ出しなし・実行時エラー表示なし。サブスクの契約者と個別契約、金庫の差額→確認記録、立替明細、要望→商品名入りの登録→キャンセル、個別キャンペーン、移行候補→旧残高等のプレビュー、監査→対象の立替を確認。390pxのサブスク追加フォームも余白内へ調整。ブラウザから管理側の保存・精算・送信は実行していない。

既存の各一覧の取得上限は基本的に維持している。これらを全履歴の件数や金銭集計の根拠へ流用するものではない。価格監視は従来どおり準備中。全機能の実データでの操作確認と本人の使いやすさ評価は未実施。この表だけを本番反映の証拠とはしない。

## 管理者による注文の残高精算

利用者一覧 → 選択した利用者の注文（古い未精算は「取引・未精算」）→ 注文詳細 → 「利用者の残高から精算」。主メニューに精算専用の新しい入口は増やさない。既存の「精算完了」は現金受領と誤解しないよう「現金を受領」と表記する。

対象は処理完了済み・未精算の現金注文と現金回収予定の後払い注文。ポイント利用後の未精算額、現在残高、精算後残高を表示し、本人確認・現金未受領の確認と精算理由を要求する。残高不足や更新競合では実行せず、注文詳細を保持する。元の支払い方法、残高の前後、理由は注文詳細と監査記録から確認できる。

管理者認証は既存のSlackログインとユーザーに結び付いた署名付き管理パスワード確認を使う。ブラウザが指定した利用者ID・操作者IDは採用しない。新しいDB関数はservice_roleだけ実行できる。注文・残高・要回収額・変更前の証跡・監査を1トランザクションで保存し、重複要求は引き落とさない。現金受領・一括精算・チャージ返金も同じロック順で処理する。古い残高スナップショットを上書きする経路は相対増減へ置換する。

購入当時の明細・在庫・ポイントは変更しない。現金を受領したことにはせず、未払いのチャージ代は要回収に残す。実際の支払い方法を残高へ変更するため、既存の注文返金・取消は引き落とした残高を1回だけ戻せる。精算記録自体は削除しない。

DB移行は履歴行の金額・残高を修正せず、準備完了フラグと変更証跡の表、service_role専用関数を追加する。新規注文・チャージは処理完了まで精算を拒否する。移行から新コードの配備までに旧コードが作った行があれば未準備のまま拒否されるため、配備前後に件数を確認し、推測で準備完了や実精算を実行しない。既存SQLをまとめて再適用しない。

隔離PostgresとモックUI/APIで回帰検証する。実利用者への精算や残高補正を検証として実行しない。既存の利用者向け残高払い試作はこの管理者機能には含めない。
